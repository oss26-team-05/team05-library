# Team 05 Collaboration Rules (팀 협업 규칙)

우리 팀(Team 05)의 원활한 협업과 오픈소스 실천을 위해 합의된 규칙입니다. 모든 팀원은 `main` 브랜치에 코드를 반영할 때 아래 규칙을 엄격히 준수합니다.

---

### 1. Pull Request (PR) 크기 및 작업 단위
- **단일 책임 원칙 (Single Responsibility)**: 1개의 Issue = 1개의 작업 브랜치 = 1개의 PR을 준수합니다. 기능 추가, 버그 수정, 리팩토링, 문서 작성을 하나의 PR에 혼합하지 않습니다.
- **코드 규모 제한**: 1회 PR당 변경 코드 라인은 **100줄 내외 (±30줄)**를 권장하며, 불가피한 경우가 아니면 200줄을 초과하지 않습니다. 대규모 변경이 필요할 경우 하위 작업 단위로 분할하여 순차적으로 PR을 생성합니다.
- **PR 템플릿 준수**: PR 생성 시 `.github/PULL_REQUEST_TEMPLATE.md`의 필수 섹션(What, Why, How I tested, AI use, Checklist)을 누락 없이 충실히 작성합니다.

---

### 2. 코드 리뷰 (Code Review) 및 피드백 정책
- **필수 승인 기준**:
  - 일반 기능(Feature) 및 버그 수정(Fix) PR: **최소 1명 이상**의 팀원 승인(Approve) 필수
  - 팀 규칙, 프로젝트 제안서, 아키텍처 등 코어 구조 변경 PR: **최소 2명 이상**의 팀원 승인 필수
- **리뷰 SLA (Service Level Agreement)**: PR 등록 후 **48시간 이내**에 리뷰 코멘트 또는 승인을 완료합니다.
- **리뷰 태그 규약**:
  - `blocking:` 결함, 요구사항 불일치 등 머지 전 반드시 수정되어야 하는 차단 이슈
  - `suggestion:` 더 나은 설계나 성능 개선을 위한 제안 (선택적 반영)
  - `question:` 구현 의도 및 동작 로직 질의
  - `nit:` 사소한 코드 스타일, 네이밍, 주석 다듬기
- **의견 충돌 해결**: 리뷰 스레드에서 2회 이상 이견이 좁혀지지 않을 경우, 팀장 중재 하에 제3의 리뷰어를 배정하거나 오프라인/비대면 회의를 통해 최종 결정합니다.

---

### 3. 브랜치 통합 및 배포 정책 (Merge Policy)
- **머지 권한**: 모든 필수 테스트 및 검증을 통과하고 규정된 수의 Approve를 획득한 후, **마지막 승인을 완료한 리뷰어**가 머지를 진행합니다. (작성자의 셀프 머지 엄격히 금지)
- **머지 전략**: 히스토리 추적성 및 분기 보존을 위해 **`Create a merge commit`**을 기본 전략으로 사용합니다.
- **리소스 정리**: 머지 완료 즉시 작업 브랜치를 삭제(Delete branch)하여 원격 저장소를 청결하게 유지합니다.
- **로컬 동기화**: 머지 직후 모든 팀원은 로컬 `main` 브랜치로 전환하여 최신 형상을 동기화합니다 (`git switch main && git pull`).

---

### 4. 브랜치 네이밍 컨벤션
작업 브랜치는 목적에 따라 표준화된 접두사를 사용하여 명명합니다:
- `feat/<feature-name>`: 새로운 이미지 전처리 모듈 및 기능 개발 (예: `feat/brightness-norm`)
- `fix/<bug-name>`: 결함 및 예외 처리 수정 (예: `fix/zero-division`)
- `docs/<doc-name>`: 마크다운 문서 및 독스트링 추가·수정 (예: `docs/team-rules`)
- `chore/<task-name>`: 라이선스, 환경설정, 빌드 파이프라인 관리 (예: `chore/mkdocs-setup`)

---

### 5. 커밋 메시지 컨벤션 (Conventional Commits)
커밋 메시지는 작업 성격을 명확히 드러내도록 표준 접두사를 적용합니다:
- `feat: 이미지 밝기 정규화 함수 구현`
- `fix: 히스토그램 스트레칭 분모 0 예외 처리`
- `docs: 팀 협업 규칙 및 proposal.md 업데이트`
- `test: 대비 조정 함수 단위 테스트 케이스 추가`
- `chore: GitHub Actions 자동 배포 파이프라인 설정`

---

### 6. AI 활용 및 공시 정책 (AI Disclosure Policy)
- GitHub Copilot, ChatGPT, Claude 등 AI 어시스턴트 사용을 허용하되, 투명하게 공시합니다.
- 모든 PR 본문의 `## AI use` 항목에 **도구명(Tool), 적용 대상(Where: 파일/함수명), 사용 범위(How: 초안 생성/리팩토링 등), 직접 수정 및 검증한 내역(After)**을 명확히 기록합니다.
  - *작성 예시*: `Claude Code를 사용하여 core.py의 adjust_contrast() 초안 생성. 루프 인덱스 경계 오류를 수동 수정하고 doctest를 직접 추가함.`
- **제재 사항**: `## AI use`를 공란으로 두거나 "AI 사용"과 같이 모호하게 기재하는 행위를 금지하며, 적발 시 해당 PR 기여도는 무효 처리됩니다.
- 생성된 모든 코드는 작성자가 동작 원리를 완전히 숙지하고 설명할 수 있어야 합니다.

---

### 7. 팀 커뮤니케이션 및 이슈 관리
- **실시간 소통**: 카카오톡 팀 메신저 (PR 리뷰 요청, 긴급 공지)
- **비동기 이력 관리**: GitHub Issues 및 Discussions (기능 요구사항 정의, 버그 리포트, 작업 할당)
- **정기 동기화**: 정규 실습 시간 및 스프린트 단위 비대면 회의

---

### 8. 품질 보증 및 시각적 검증 규약 (Visual Quality Assurance)
- **전처리 시각 검증 의무화**: 이미지 처리 결과에 영향을 주는 기능 추가·수정 PR에는 정량적 검증 결과와 함께 **Before(원본 이미지) / After(보정·복원 결과물) 비교 이미지**를 PR 본문에 필수로 첨부합니다. 비교에는 동일한 원본 이미지를 사용하고, 적용한 함수와 주요 매개변수를 함께 기록합니다.
- **첨부 예외**: 문서나 설정만 변경하고 이미지 처리 결과에 영향을 주지 않는 PR은 비교 이미지를 생략할 수 있습니다. 이 경우 PR 본문의 `How I tested`에 변경 사항을 확인한 방법을 작성합니다.
- **첨부 방식**: 비교 이미지는 PR 본문에 직접 첨부합니다. 용량이 큰 영상은 외부 링크를 활용할 수 있으며, 모든 팀원이 별도 접근 요청 없이 확인할 수 있도록 공유 권한을 설정합니다.
- **결과 재현성 검증**: 리뷰어는 첨부된 검증 결과와 비교 이미지를 확인합니다. 개선 효과가 모호하거나 재현 여부를 확인할 필요가 있으면, 동일한 샘플 데이터와 매개변수로 로컬에서 실행한 뒤 승인 여부를 결정합니다.
